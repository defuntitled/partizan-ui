# partizan — клиент для Android, спецификация проекта

## Обзор

Нативный клиент partizan для Android на Flutter. Он подключается к серверу partizan по тому же протоколу, что клиенты для Linux и OpenWrt, и направляет в туннель трафик системы по правилам раздельного туннелирования (по IP-адресам и подсетям). В отличие от роутерного клиента, источник трафика здесь не SOCKS5, а системный TUN-интерфейс через `android.net.VpnService`.

Flutter выбран, чтобы позже переиспользовать тот же UI для десктопной версии (Linux, Windows, macOS). Бизнес-логика туннеля остаётся в Rust: мобильный клиент — это тонкая обёртка над существующим crate `client-core`, как и было заложено в основной спецификации (`spec/partizan_spec.md`, раздел «Скоуп и roadmap платформ»).

**Цели**

- Список серверов с хранением нескольких профилей и редактированием их названий.
- Импорт сервера из ссылки `partizan://…` (вставка строки и QR-код).
- Подключение к выбранному серверу по протоколу partizan (QUIC с фолбэком на TCP+TLS).
- Раздельное туннелирование: выбранные адреса и подсети идут через туннель, остальной трафик — напрямую.
- Переиспользуемый UI для будущего десктопа.

**Не-цели (на первую версию)**

- iOS. Архитектура это предусматривает (общее Rust-ядро), но Network Extension и его ограничения — отдельная работа.
- ABI, кроме arm64-v8a. Собираем только под arm64 (armv8); armv7 и x86_64 (эмулятор) пока не планируются, но структура сборки оставляет возможность добавить их позже.
- Раздельное туннелирование по приложениям (per-app). За скоупом проекта целиком, не только первой версии (см. «Раздельное туннелирование»).
- Встроенный выпуск или смена серверных сертификатов, управление устройствами на сервере. Клиент только потребляет ссылку подключения.
- Раздельное туннелирование по доменам и локальный DNS-прокси (fake-IP) под него. За скоупом проекта: правила задаются по IP-адресам и подсетям. От DNS-утечек защищает заведение DNS-трафика в туннель (см. «Раздельное туннелирование» → DNS), а не собственный резолвер.

**Термины**

| Термин | Значение |
| --- | --- |
| Профиль сервера | Запись в списке: имя плюс разобранная `ConnectionUri` (хост, порт, токен, pin, транспорт) |
| Ядро | Rust-код `client-core` + `transport` + `proto`, собранный в нативную библиотеку под Android |
| FFI-мост | Тонкий слой между Dart и ядром (UniFFI → Kotlin/JNI), по которому идут команды и статус |
| TUN | Виртуальный сетевой интерфейс от `VpnService`, с которого читаются IP-пакеты приложений |
| Источник трафика | То, что отдаёт движку `TcpRequest` и `UdpPacket`; на Android это TUN + userspace-стек, а не SOCKS5 |
| Раздельное туннелирование | Правила, по которым часть трафика идёт в туннель, а часть — напрямую |

## Архитектура

Слои повторяют основную спецификацию: платформы различаются только верхним рядом, а `client-core`, `transport` и `proto` переиспользуются без изменений. Для Android добавляются три новых слоя — FFI-мост, источник трафика из TUN и UI на Flutter.

```
Flutter UI (Dart)            # экраны: список серверов, переключатель, настройки раздельного туннелирования
      │  method channel / FFI
Kotlin: VpnService + мост    # жизненный цикл VPN, TUN fd, уведомление, автозапуск
      │  UniFFI
client-ffi (Rust, новый)     # фасад над client-core: start/stop, статус, конфиг
      │
tun (Rust, новый)            # источник трафика: TUN fd → userspace TCP/IP → TcpRequest/UdpPacket
      │
client-core  →  transport  →  proto     # без изменений, общие с сервером и роутером
```

Ключевой принцип: **ничего специфичного для Android не попадает в `client-core` и ниже**. Движок уже принимает абстрактные `TcpRequest` и `UdpPacket` и ничего не знает про источник. Новый crate `tun` реализует тот же источник трафика, что `socks5` реализует для роутера. Это прямое продолжение архитектурного ограничения из `CLAUDE.md`: «`client-core` takes abstract `TcpRequest` / `UdpPacket`; it must not know about SOCKS5 (future TUN sources plug in instead)».

**Почему TUN, а не SOCKS5.** На роутере трафик в клиент заводит podkop. На телефоне нет внешнего маршрутизатора, перехват делает сама система через `VpnService`: приложение получает файловый дескриптор TUN и читает оттуда IP-пакеты. Поэтому клиенту нужен userspace TCP/IP-стек, который превращает пакеты в потоки и датаграммы.

**Почему свой стек на `smoltcp`, а не готовый tun2socks.** Готовые tun2socks (badvpn, hev-socks5-tunnel и подобные) выводят трафик в SOCKS5, то есть требуют поднять на устройстве слушающий SOCKS5-порт. Это нежелательно: локальный открытый прокси-порт обнаруживают сканеры приложений (антивирусы, security-аудиторы, да и малварь) и он сам по себе демаскирует клиент. Поэтому TUN-пакеты разбираются `smoltcp` прямо в процессе и отдаются движку как `TcpRequest`/`UdpPacket`, без слушающего сокета и без SOCKS5 на устройстве. Crate `socks5` на Android не используется (он остаётся только для роутера).

**Новые Rust-crate**

| Crate | Назначение | Зависит от |
| --- | --- | --- |
| `tun` | Userspace TCP/IP поверх TUN fd: разбор IP-пакетов, сборка `TcpRequest` и `UdpPacket`, запись ответных пакетов обратно в TUN | `client-core`, `smoltcp` |
| `client-ffi` | Фасад для мобильных платформ: старт/стоп движка, статус, передача конфига и TUN fd, колбэки | `client-core`, `tun`, `uniffi` |

`tun` и `client-ffi` уже зарезервированы в `spec/partizan_spec.md` («позже: client-ffi/ (UniFFI), tun/»). Эта спецификация их раскрывает.

**Что переиспользует десктоп.** Dart-слой (экраны, модель состояния, хранилище профилей) общий. Платформенная часть различается: на Android — `VpnService`, на десктопе — права на TUN и системные маршруты. `client-ffi` и `tun` общие для всех платформ, где есть TUN.

| Задача | Технология | Почему |

| Ядро | `client-core`, `transport` (feature `chrome`), `proto` | Без изменений |

BoringSSL (feature `chrome`) под Android собирается так же, как под Linux: нужны cmake, C/C++-компилятор и libclang в CI. Профиль Chrome и ожидаемый JA4 — те же, что в `crates/transport/src/chrome.rs`.

## FFI-мост (`client-ffi`)

Мост держит минимальную асинхронную поверхность. Движок `client-core` уже управляет сессией сам (супервайзер, бэкофф, фолбэк, `GoAway`); мост только запускает его и отдаёт наружу статус.

```rust
// Упрощённо, фактический IDL — в client-ffi через UniFFI.

/// Конфиг запуска, собранный из профиля на стороне Dart.
pub struct VpnConfig {
    pub uri: String,              // строка partizan://… из профиля
    pub split: SplitConfig,       // правила раздельного туннелирования
    pub mtu: u16,                 // MTU TUN-интерфейса
}

/// Правила маршрутизации трафика.
pub struct SplitConfig {
    pub mode: SplitMode,          // Include | Exclude
    pub routes: Vec<IpNet>,       // адреса и подсети, к которым применяется mode
}

pub enum SplitMode {
    /// В туннель идут только перечисленные подсети, остальное напрямую.
    Include,
    /// В туннель идёт всё, кроме перечисленных подсетей.
    Exclude,
}

/// Снимок состояния для UI (отражает client_core::Status).
pub struct VpnStatus {
    pub state: VpnState,          // Idle | Connecting | Connected | Reconnecting | Revoked | Error
    pub transport: Option<String>,// "quic" | "tls"
    pub rtt_ms: Option<u32>,
    pub tx_bytes: u64,
    pub rx_bytes: u64,
    pub reconnects: u64,
    pub error: Option<String>,
}

pub trait StatusListener: Send + Sync {
    fn on_status(&self, status: VpnStatus);
}

/// Принимает уже открытый TUN fd от VpnService и поднимает туннель.
/// Возвращается сразу; дальнейшие изменения приходят через listener.
fn start(tun_fd: i32, config: VpnConfig, listener: Box<dyn StatusListener>) -> Result<(), VpnError>;

/// Останавливает туннель и закрывает сессию.
fn stop();

/// Текущий статус (для опроса, помимо колбэков).
fn status() -> VpnStatus;

/// Проверяет ссылку без подключения (для экрана импорта): парсинг + пробное соединение.
fn check_uri(uri: String) -> Result<CheckResult, VpnError>;

/// Включает/выключает профилирование и подробный лог userspace-стека на лету.
fn set_diagnostics(profiling: bool, verbose_log: bool);

/// Снимок метрик стека для экрана диагностики (пусто, если профилирование выключено).
fn stack_metrics() -> StackMetrics;
```

- `tun_fd` открывает `VpnService` на стороне Kotlin и передаёт целым числом; ядро читает и пишет IP-пакеты прямо в него.
- Токен не пересекает FFI в открытом виде отдельно: он часть `uri`, которую Dart достаёт из защищённого хранилища только на момент старта. В логах ядра токен не появляется (правило из `CLAUDE.md`).
- `check_uri` переиспользует `client_core::check_transport`: для `transport=auto` достаточно одного рабочего транспорта.

**Как реализовано (A03–A04).**

- **Маршруты.** В `SplitConfig.routes` подсети передаются строками (`"99.84.0.0/16"`) и разбираются в ядре. Некорректная запись даёт `VpnError::InvalidConfig` с текстом этой записи.
- **`CheckResult`.** Содержит `host` и `port` (по ним строится имя профиля по умолчанию), а также время установки сессии по QUIC и по TCP+TLS: `quic_ms`, `tls_ms`. Вызов блокирующий, его нужно делать не из UI-потока.
- **Владение fd.** `start` забирает fd во владение: Kotlin вызывает `ParcelFileDescriptor.detachFd()`. Ядро переводит fd в неблокирующий режим и закрывает его в `stop`.
- **`stop`.** Корректно закрывает сессию (`Engine::shutdown`), останавливает стек и рантайм, затем отправляет в listener финальный `Idle`.
- **Повторный запуск и статус.** Повторный `start` без `stop` возвращает `AlreadyRunning`. `status()` отдаёт снимок, который обновляется раз в 500 мс; изменения приходят в listener.
- **Kotlin-пакет и AAR.** Пакет — `partizan.core`, AAR — `partizan-core.aar`, библиотека — `libclient_ffi.so` (рядом `libc++_shared.so` для BoringSSL). Приложение подключает AAR и JNA: `net.java.dev.jna:jna:<версия>@aar`. В AAR лежат consumer-правила R8 для JNA и биндингов.
- **Диагностика.** `set_diagnostics` и `stack_metrics` уже есть в мосте. В A11 остаётся только UI.

## Источник трафика из TUN (`tun`)

Crate `tun` — это то же, что `socks5` для роутера: он реализует источник трафика для `client-core`, только вместо SOCKS5-протокола разбирает IP-пакеты.

- **Чтение.** Из TUN fd читаются IP-пакеты (IPv4 и IPv6). `smoltcp` в режиме userspace-стека собирает из них TCP-соединения и UDP-потоки.
- **TCP.** На новое соединение формируется `TcpRequest { dst, io }`, где `dst` — адрес назначения из заголовка пакета, `io` — локальная сторона соединения внутри `smoltcp`. Движок открывает tunnel stream и копирует байты в обе стороны.
- **UDP.** На каждый источник (пара локальный адрес/порт) заводится `UdpFlow`; датаграммы уходят как `UdpPacket`, ответы (`UdpReply`) пишутся обратно в TUN.
- **Адреса — это IP, не домены.** На телефоне перехват идёт на уровне IP-пакетов, поэтому имя назначения уже разрешено системным резолвером до попадания в TUN. В туннель уходит IP. Это отличается от роутера, где podkop может отдавать домен. Как следствие: DNS-запросы тоже видны как UDP на порт 53 и идут через туннель по общим правилам (см. ниже про DNS).
- **MTU.** TUN поднимается с MTU около 1400, чтобы инкапсулированный пакет помещался в QUIC DATAGRAM без фрагментации (медиапакеты WebRTC около 1200 байт проходят целиком).
- **DNS.** Здесь главный риск утечки. К моменту попадания пакета в TUN домен уже разрешён системным резолвером, то есть сам DNS-запрос уходит раньше любого TCP-соединения. Если он не заведён в туннель, провайдер видит все домены — даже те, что потом ходят через VPN. Поэтому DNS-трафик (UDP и TCP на порт 53, а также DoT на 853) **всегда** заводится в туннель, независимо от режима раздельного туннелирования. В `VpnService` это делается через `Builder.addDnsServer(...)` и/или маршрут на DNS-сервер, так что система шлёт DNS в TUN. Встроенный резолвер для этого не нужен; он понадобился бы только при раздельном туннелировании по доменам, которое за скоупом проекта. DoH (DNS-over-HTTPS) специально не обрабатываем: по порту он не отличается от обычного HTTPS, так что в режиме Include запросы приложения или системы по DoH могут идти мимо туннеля. Это принятое ограничение, а не пробел; при необходимости пользователь отключает DoH в системных настройках или в приложении.

### Диагностика userspace-стека

Userspace TCP/IP на слабых телефонах может упираться в CPU, поэтому в `tun` сразу закладываются средства наблюдения, управляемые тоглами в настройках приложения. По умолчанию всё выключено — чтобы не трогать производительность и не писать лишнего.

- **Тогл «Профилирование стека».** Включает сбор метрик `tun`: пакетов в секунду, время обработки пакета (p50/p99), глубина очередей, число активных TCP-соединений и UDP-потоков, доля времени в стеке против ввода-вывода. Метрики видны на экране диагностики и уходят в лог.
- **Тогл «Подробный лог стека».** Поднимает уровень логов `tun` (разбор пакетов, события соединений). Адреса назначения — только на этом уровне и только локально, как и в ядре; токены не логируются никогда.
- **Экспорт.** Собранные метрики и лог выгружаются одним файлом по явному действию (кнопка на экране диагностики), для разбора узких мест и прикрепления к issue.
- Тоглы прокидываются через `client-ffi` в `tun`: включение и выключение на лету, без перезапуска туннеля. Когда профилирование выключено, счётчики не считаются (нулевой оверхед), а не просто скрыты.

## Раздельное туннелирование

Раздельное туннелирование — это свойство источника трафика и `VpnService`, а не протокола. Протокол partizan не меняется. Реализуется на двух уровнях.

**По подсетям (первая версия).** Пользователь задаёт список адресов и подсетей и режим:

- **Include (по умолчанию для обхода блокировок):** в туннель идут только перечисленные подсети, остальное — напрямую. На уровне `VpnService` это выражается как `addRoute` только для этих подсетей, так что система сама отправляет в TUN лишь нужные пакеты.
- **Exclude:** в туннель идёт весь трафик, кроме перечисленных подсетей. Выражается через `addRoute("0.0.0.0/0")` плюс `excludeRoute` для исключений (Android 13+); на более старых версиях — через разбиение диапазона `0.0.0.0/0` на подсети минус исключения.

**Вторая линия в `tun`.** Пакеты, которые всё же попали в TUN (DNS, неточное разбиение диапазона на старых Android), фильтр в `tun` разводит по тем же правилам: TCP-соединение решается один раз по SYN, UDP-датаграмма — по своему адресу назначения, при пересечении подсетей решает самая специфичная. DNS (порты 53 и 853) всегда идёт в туннель. Трафик «напрямую» уходит через обычные сокеты ОС (обработчик `Direct`). Каждый такой сокет до первой отправки передаётся в `VpnService.protect(fd)`, иначе он вернётся в TUN. Правила меняются на лету, уже открытые соединения сохраняют свой путь. Счётчики переданных и полученных байт ведутся отдельно для туннеля и для прямого пути.

Список редактируется в UI: добавить/удалить запись вручную. Хранится в профиле: правила могут быть общими или своими на каждый сервер (общие по умолчанию, переключатель в настройках).

**Импорт адресов и подсетей из файла.** Обязательная функция первой версии: список правил можно загрузить из текстового файла. Формат — адреса и CIDR-подсети через запятую, например:

```
99.84.0.0/16, 99.86.0.0/16, 203.0.113.7, 2606:4700::/32
```

Разбор: разделитель — запятая, пробелы и переводы строк вокруг записей игнорируются, пустые записи пропускаются, поддерживаются IPv4, IPv6 и одиночные адреса (трактуются как `/32` и `/128`). Парсер устойчив к мусору: некорректная запись не роняет импорт, а возвращается пользователю списком отклонённых строк. Импортированные правила добавляются к текущему списку (с дедупликацией) либо заменяют его — выбор в диалоге импорта. Экспорт списка в тот же формат — для переноса между устройствами и профилями.

**По доменам — за скоупом.** Раздельное туннелирование по доменам (правила вида `*.example.com`) в проект не входит: оно требует знать домен в момент соединения, а в TUN приходит уже IP, то есть нужен локальный DNS-прокси с fake-IP. Это отдельная работа и отдельная спецификация. Правила задаются только по IP-адресам и подсетям.

**По приложениям — за скоупом.** `VpnService` в принципе умеет `addAllowedApplication` / `addDisallowedApplication` («эти приложения через VPN» или «все, кроме этих»), но раздельное туннелирование по приложениям в этот проект не входит и в модель данных не закладывается. Если понадобится позже — это отдельная спецификация.

**Проверка на петли.** Трафик самого ядра к серверу VPN не должен попадать обратно в TUN. `VpnService` исключает собственное приложение через `addDisallowedApplication(packageName)` или сокеты защищаются `VpnService.protect(fd)`. Это обязательный шаг, иначе образуется петля.

## Хранение и безопасность

- **Профили.** Список серверов в SQLite (`drift`): `id`, `name` (редактируемое), `order`, параметры подключения без токена, правила раздельного туннелирования. Токен и вся строка `partizan://…` — в Android Keystore через `flutter_secure_storage`, под ключом профиля.
- **Токен** достаётся из защищённого хранилища только в момент старта и сразу передаётся в ядро как часть URI. Не логируется, не кладётся в обычные настройки, не попадает в бэкапы (флаг `allowBackup=false`, исключение secure storage из автобэкапа).
- **Pin.** SPKI pin из ссылки проверяется ядром так же, как на других клиентах. Для самоподписанного сертификата сервера pin обязателен; `insecure=1` только для отладочных сборок.
- **Keystore и биометрия.** Опционально — требовать разблокировку (биометрия/PIN) перед стартом VPN, если профиль помечен как чувствительный.
- **Логи.** На устройстве — минимальный уровень, без токенов и без адресов назначения выше `debug`, как в ядре. Экспорт логов для диагностики — по явному действию пользователя.
- **Нетехнический риск.** Публикация и распространение инструмента обхода блокировок в некоторых юрисдикциях несёт риски, не связанные с кодом; это вне зоны ответственности спецификации, но стоит учитывать при публикации в сторах.

Поведение состояния на главном экране зеркалит `VpnState`: `Idle → Connecting → Connected`, при обрыве `Reconnecting`, при отзыве устройства `Revoked` с явным сообщением и без попыток переподключения.

**Поверхности быстрого управления.** Помимо экранов включать и выключать туннель можно, не открывая приложение. Это нативные компоненты Android поверх тех же `start`/`stop`/`status`, а не экраны Flutter.

- **Плитка в Quick Settings** (шторка быстрых настроек Android) через `TileService`: нажатие поднимает активный профиль или опускает туннель, плитка показывает состояние (активна/неактивна). Если активного профиля нет, нажатие открывает приложение на экране выбора сервера. Запуск VPN из плитки учитывает, что системный диалог разрешения мог не быть показан — тогда плитка ведёт в приложение.
- **Виджет на домашнем экране** (App Widget): кнопка включения/выключения, текущее состояние и имя активного сервера. Обновляется по изменению `VpnState`. На десктопе аналога нет, это только Android; Flutter-часть не затрагивается.

Обе поверхности отражают одно состояние с приложением и уведомлением: источник правды — `VpnState` из ядра, а не локальные флаги компонентов.

## Жизненный цикл VpnService

- `prepare()` запрашивает у пользователя разрешение на VPN (системный диалог) при первом запуске.
- При старте Kotlin строит TUN через `VpnService.Builder`: адреса интерфейса, MTU, маршруты по правилам раздельного туннелирования, `addDisallowedApplication(self)`.
- Открытый TUN fd передаётся в `client-ffi::start`. Ядро живёт в своём потоке/рантайме, не блокируя UI.
- Foreground-служба с постоянным уведомлением (требование Android), в уведомлении — состояние и кнопка «отключить».
- Quick Settings-плитка (`TileService`) и домашний виджет (App Widget) переключают туннель и отражают `VpnState`; обновляются из службы при каждом изменении состояния.
- `onRevoke()` (пользователь или система отозвали VPN) → `stop()` в ядре, очистка.
- Автозапуск при загрузке и режим «всегда включён» — через системные механизмы Always-on VPN; приложение к ним готово, но не обходит их.

## Декомпозиция по коммитам

Нумерация продолжает основной план (`spec/partizan — decompozition.md` заканчивается на C26). Каждый шаг — один коммит, собирается и проходит CI. Общий DoD и соглашения — те же, что в основном плане (формат Conventional Commits, ID тест-кейсов вида `A03-T2`, `#![forbid(unsafe_code)]` в новых чистых crate, где применимо).

## Открытые вопросы

- **Производительность userspace-стека.** На слабых телефонах userspace TCP/IP может упираться в CPU. Это диагностируется встроенными тоглами профилирования и логирования стека (см. «Диагностика userspace-стека»), а не выносится в отдельное исследование; если упор в CPU подтвердится — профилирование покажет узкое место, дальше профиль сборки или несколько рабочих потоков.
